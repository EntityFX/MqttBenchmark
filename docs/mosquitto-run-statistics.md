# Статистика и выводы прогона Mosquitto (локально, без Docker)

Документ содержит статистическую обработку полного прогона (72/72 ключей, 24 точки,
3 повтора каждая) и выводы о пригодности данных.

Исходные данные: `results/aggregated/mosquitto-local-native/broker-observations.v3.json`.
Контекст стенда и ограничения — в [mosquitto-local-run-analysis.md](mosquitto-local-run-analysis.md).

**Главный вывод.** Пакет публикации Mosquitto исправен (0 отказов, 0 дубликатов на
1.5 млн сообщений), но метрика `deliveryLossRate` **недействительна**: потери
измеряют пропускную способность единственного синхронно-логирующего подписчика
стенда, а не брокер. Подробно — в разделе 5.

## 1. Методика обработки

- Каждая из 24 точек — среднее по 3 независимым повторам; в таблице приведены
  среднее, стандартное отклонение и полуширина доверительного интервала CI95
  (t-распределение, df = 2).
- Коэффициент вариации (CV) считается по трём повторам одной точки.
- Доля доставки = `uniqueDeliveries / completedPublishes`.
- «Потолок подписчика» — максимальное число доставок за одну секунду, наблюдённое
  в `deliveries.ndjson`.

## 2. Воспроизводимость внутри точки

| Метрика | Значение |
| --- | --- |
| CV по 3 повторам, минимум | 0.4 % (`m256.q2.p1`) |
| CV по 3 повторам, максимум | 8.3 % (`m256.q0.p1`) |
| CV по 3 повторам, медиана | 3.6 % |
| Точки с CV > 5 % | 5 из 24 |

**Вывод.** Повторяемость внутри точки хорошая: разброс укладывается в 8 % и в
большинстве случаев не превышает 5 %. Но это относится к **публикации**, которая
и была стабильной; межпоточные различия (например, QoS 1 против QoS 2)
многократно больше внутриточечного шума, поэтому разделение по QoS статистически
значимо. Для QoS 0 при 1 издателе разброс выше — это самая «быстрая» точка, где
относительная дисперсия счётчика накапливается быстрее всего.

## 3. Пропускная способность

`completedRps`, 256 байт payload (для 16 байт результаты статистически неотличимы):

| publishers | QoS 0 | QoS 1 | QoS 2 | QoS2 / QoS1 |
| --- | --- | --- | --- | --- |
| 1 | 27 210 | 6 664 | 4 912 | 0.74 |
| 16 | 51 052 | 35 256 | 22 638 | 0.64 |
| 64 | 52 148 | 40 019 | 22 276 | 0.56 |
| 128 | 50 525 | 43 856 | 22 722 | 0.52 |

Масштабирование:

| QoS | p1 → p16 | p16 → p128 | Плато |
| --- | --- | --- | --- |
| 0 | ×1.9 | −1 % | ~51 тыс. RPS уже при 16 издателях |
| 1 | ×5.3 | +24 % | растёт до 128 |
| 2 | ×4.6 | 0 % | ~22.7 тыс. RPS уже при 16 издателях |

**Вывод 1. Потолок определяется числом ядер, а не числом клиентов.** При QoS 0
пропускная способность выходит на плато ~51 тыс. RPS при 16 издателях и далее
не растёт (p128 фактически ниже p16). Это ожидаемо для однопоточного Mosquitto,
закреплённого за одним ядром: добавление клиентов не даёт новых ядер обработки.

**Вывод 2. Гарантии QoS оплачиваются пропускной способностью, и с ростом числа
издателей штраф уменьшается.** Отношение QoS2/QoS1 падает с 0.74 при одном
издателе до 0.52 при 128. Причина: при одном издателе узкое место — round-trip
(одно сообщение за раз), и четыре шага QoS2 бьют по нему сильнее всего; при
128 издателях брокер обрабатывает поток и QoS1/2 успевают конвейеризоваться.

**Вывод 3. Размер payload не влияет на пропускную способность.** Разница между
16 и 256 байт составляет от −7 % до +5 % без систематического знака и укладывается
в межпоточечный шум (CV до 8 %). В диапазоне 16–256 байт обработка на стороне
брокера не зависит от размера сообщения — протокольный оверхед доминирует.

## 4. Латентность публикации

p99, мс (256 байт):

| publishers | QoS 1 | QoS 2 |
| --- | --- | --- |
| 1 | 0.184 | 0.268 |
| 16 | 0.841 | 1.414 |
| 64 | 4.253 | 5.933 |
| 128 | 12.725 | 12.119 |

Рост p99 от 1 к 128 издателям: **×69 для QoS 1**, **×45 для QoS 2**.

**Вывод 4. Латентность растёт нелинейно и опережает рост числа издателей.**
При QoS 1 пропускная способность выросла на 24 % (p16 → p128), а p99 — в 15 раз
(0.84 → 12.7 мс). Это признак исчерпания очередей: клиенты успевают публиковать,
но подтверждения задерживаются. Именно этот эффект объясняет, почему QoS1 при 128
издателях формально быстрее, чем при 16 — часть пакетов «уходит» ценой
накопления задержки.

**Вывод 5. Максимальная латентность (max) достигает 80–97 мс уже при 64–128
издателях** и слабо зависит от QoS — это хвост распределения, общий для обоих
уровней, вероятнее всего связанный с GC и планированием в генераторе на том же
хосте.
## 5. Потери доставки: диагностика

Доля доставки (полученное от завершённых публикаций):

| publishers | QoS 0 | QoS 1 | QoS 2 |
| --- | --- | --- | --- |
| 1 | 100 % | 100 % | 100 % |
| 16 | 100 % | 9–11 % | 8–9 % |
| 64 | 30–60 % | 7–18 % | 2–3 % |
| 128 | 44–91 % | 12–13 % | 1–2 % |

Потолок подписчика (макс. доставок за секунду) по QoS:

| QoS | Наблюдаемый потолок | Поведение |
| --- | --- | --- |
| 0 | 55–223 тыс./с | не ограничен (fire-and-forget, нет обратного давления) |
| 1 | 3.6–11 тыс./с | растёт с числом издателей, затем упирается |
| 2 | **1 027–1 034/с** | константа, не зависит от числа издателей |

**Вывод 6. Потери измеряют не брокер, а подписчик самого стенда.** Решающий
аргумент — QoS 2: потолок подписчика равен ~1 030 доставок/с и **не меняется** при
росте числа издателей с 16 до 128. Свойство брокера не может быть константой,
не зависящей от нагрузки; константа — это предел приёмника. При этом брокер
продолжал подтверждать публикации без единой ошибки (`publishFailureRate = 0`).

Причина найдена в коде стенда
(`src/EntityFX.MqttBenchmark.Campaign/Workload/CampaignWorkloadRunner.cs`):
подписчик единственный, и в его обработчике `ApplicationMessageReceivedAsync`
**синхронно** пишет строку NDJSON в файл под глобальным замком:

```csharp
lock (deliveryGate) {
    ledger.Deliver(id, seconds);
    deliveryLog.Write(new { id, elapsedSeconds = seconds, payloadBytes = payload.Count });
}
```

Синхронная запись на диск на каждое сообщение под блокировкой ограничивает
приёмник величиной ~1 тыс. записей/с при QoS 2. QoS 0 ограничения не показывает,
поскольку не имеет обратного давления и не ждёт подтверждений.

Дополнительное подтверждение: `drainReason` для всех проблемных точек —
`quietPeriod` (2.8–3.2 с), а не `allCompletedDelivered`. Дренаж завершался по
таймауту тишины, тогда как в брокере ещё оставалась очередь. Для QoS 2 поток
доставок продолжался до конца окна измерения (t = 35 с при старте измерения
t = 5 с), то есть подписчик был насыщен непрерывно, а не «догонял после всплеска».

**Вывод 7. Метрика `deliveryLossRate` в текущей реализации стенда непригодна для
калибровки MqttY** при любом числе издателей ≥ 16. Она измеряет пропускную
способность однопоточного обработчика доставок, а не потери брокера. Значения
0.85–0.99 нельзя интерпретировать как поведение Mosquitto.

## 7. Итоговые выводы

1. **Пакет публикации Mosquitto 2.0.15 исправен** при 38–52 тыс. сообщений/с на
   одном ядре: нулевой отказ публикаций, корректные идентификаторы, отсутствие
   дубликатов.
2. **Потолок ~51 тыс. RPS (QoS 0) — свойство однопоточности**, а не числа
   клиентов. Дальнейшее масштабирование требует параллельных экземпляров
   брокера, а не дополнительных издателей.
3. **Отношение QoS2/QS1 уменьшается с ростом нагрузки** (0.74 → 0.52) из-за
   конвейеризации handshake при большем числе одновременных сессий.
4. **Размер payload в диапазоне 16–256 байт не влияет** на пропускную
   способность (−7…+5 %, в пределах шума).
5. **p99 латентности растёт нелинейно** (×69 для QoS1), опережая рост
   пропускной способности — признак исчерпания очередей, а не улучшения
   масштабирования.
6. **Метрика потерь доставки недействительна** из-за единственного
   синхронно-логирующего подписчика в стенде. Это дефект стенда, а не брокера,
   и он блокирует калибровку MqttY по методу BrokerFidelity.
7. **Прогон не является диссертационно-годным** как источник данных: хост не
   изолирован, guard работал с ослабленным интервалом (3 с вместо 1.25 с),
   лимит памяти не enforceable (нет прав на cgroup v2), брокер и генератор делят
   одну машину.

## 8. Исправления: что сделано и что осталось

### 8.1. Выполнено: буферизация журнала доставок

Обработчик доставки писал NDJSON синхронно под глобальным замком прямо в сетевом
callback'е. Добавлен `BufferedEventLog` (`src/EntityFX.MqttBenchmark.Campaign/Workload/BufferedEventLog.cs`):
запись сериализуется в callback'е и уходит в неограниченную очередь, диск занимает
отдельный поток. Порядок записей сохраняется, буфер не ограничен (потеря доказательств
недопустима), а сброс awaited до возврата из `RunAsync` — иначе SHA-256 запечатывание
попытки не покрыло бы журнал.

Покрыто тестами: `BufferedEventLogTests` (порядок, полнота, сброс перед dispose,
неблокирующий enqueue) и `RunFlushesBufferedDeliveriesBeforeTheAttemptIsSealed`.

**Измеренный эффект** на худшей точке (256 байт, QoS 2, 64 издателя, Mosquitto 2.0.15):

| Показатель | До | После |
| --- | --- | --- |
| Потолок подписчика | ~1 030 msg/s | ~1 275 msg/s (+24 %) |
| deliveryLossRate | 97.72 % | 97.90 % |

### 8.2. Не устранено: узкое место находится глубже

**Потери не исчезли.** Значит, синхронная запись на диск была не единственной причиной,
и первоначальная формулировка вывода 6 («потери измеряют подписчик») верна по существу,
но объясняла лишь часть ограничения.

Наблюдаемое поведение после исправления: подписчик стабильно получает ~490 msg/s
(пик 1 275) при 23 000 msg/s публикаций, без единого разрыва потока более 2 с —
то есть сообщения не «догоняют» пачками, а теряются непрерывно. Дальнейшая локализация
предела (пропускная способность MQTTnet-клиента приёма против настроек брокера)
в объём этого прогона не входила.

**Практический вывод не меняется: `deliveryLossRate` по-прежнему непригодна для
калибровки MqttY.** До устранения узкого места метрику нельзя интерпретировать как
потери брокера.

### 8.3. Что исправлено попутно

- `CampaignDefinition.Validate` требовал строго положительный `CooldownSeconds`, хотя
  раннер трактует эту фазу как необязательную. Прогоны без cooldown были
  неконструируемыми, из-за чего транспортные интеграционные тесты падали — и этого не
  было видно, поскольку интеграционные тесты по умолчанию пропускаются.
- `BrokerStandControllerTests` запускал контроллер через жёстко зашитый `pwsh`, тогда как
  `StandLifecycle` уважает `MQB_STAND_SHELL`. На хосте без `pwsh` в `PATH` (обычная
  ситуация на Linux) 32 теста контроллера падали. Теперь оба пути используют одну
  настройку.

Совокупный эффект на интеграционных тестах: **36 падающих → 4** (оставшиеся —
предсуществующие и не связаны с этими правками; см. раздел 9).

## 9. Что нужно исправить дальше

1. **Локализовать остаточный предел приёма.** Следующий кандидат — обработка QoS 2
   в MQTTnet-клиенте приёмника и/или настройки очереди брокера (`max_inflight_messages`,
   `max_queued_messages`). Нужен отдельный изолированный эксперимент: приёмник,
   считающий сообщения без журналирования и без `DeliveryLedger`.
2. **Число подписчиков.** Сделать его пропорциональным числу издателей, иначе
   измеряется приёмник. Требует разбиения топиков, иначе все подписчики получат
   полные копии и учёт уникальных идентификаторов сломается.
3. **Политика дренажа.** Завершать по `quietPeriod` допустимо только при пустой очереди
   брокера; иначе потери неотличимы от непрочитанного бэклога.
4. **Изоляция.** Генератор и брокер на разных физических машинах, рабочий стол
   выключен; вернуть guard к 1.25 с и `--max-attempts` к 3.
5. **Ресурсные ограничения.** Запускать с правами на cgroup v2 либо явно принять
   `not-enforced-native` как блокер.

### Оставшиеся падающие интеграционные тесты (предсуществующие)

- `StandClock_RejectsMisalignmentAndRetainsOffsetEvidence` (±195),
  `StandClock_RejectsUncertainSlowProbeEvenWhenPointOffsetIsWithinThreshold` —
  фикстура `StrictDocker.ps1` управляет задержкой через docker-путь синхронизации
  часов, тогда как стенд работает в native-режиме; задержка не применяется и отказ не
  наступает.
- `AggregateCommand_PublishesV3OnlyForSealedCompleteCampaignAndRefusesOverwrite` —
  тест вызывает `aggregate` без `--stand`, который требуется для схемы v3.
