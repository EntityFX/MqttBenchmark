# Local Mosquitto run (no Docker) — analysis

Полный прогон Mosquitto в локальном профиле **без Docker**: 72/72 ключей матрицы,
24 агрегированные точки, `broker-observations.v3.json`. Этот документ — разбор
полученных данных и честная оценка их пригодности.

## 3. Интерпретация

**Путь публикации исправен.** `publishFailureRate` равен нулю во всех 72 прогонах:
1.5 млн публикаций за 30 с без единой ошибки. Латентность подтверждения мала
(p50 ≤ 0.2 мс при одном издателе). CPU-pinning работает: телеметрия показывает
`cpuScope: process-pinned`, `affinityCpus: 0`, а загрузка CPU брокера стабильно
99–100 % одного ядра — однопоточный Mosquitto полностью насыщал выделенное ядро.

**Потери доставки — артефакт топологии стенда, а не дефект брокера.** Величины
0.85–0.99 требуют осторожности и **не должны** использоваться для калибровки MqttY.
Доказательства:

1. Все проблемные точки — при ≥ 16 издателях; при одном издателе потери нулевые
   во всех QoS. Настоящий дефект брокера не появлялся бы только по числу клиентов.
2. `drainReason` для этих точек — `quietPeriod` (2.8–3.2 с), а не `allCompleted`:
   дренаж завершался по таймауту тишины, когда в брокере ещё оставалась очередь
   недоставленных сообщений.
3. При 38–52 тыс. сообщений/с единственный подписчик не успевает вычитывать поток.
   Топология `BrokerFidelity` создаёт N издателей и **одного** подписчика, поэтому
   именно он становится узким местом.

Пример: `m256.q1.p64.r1` — 1 140 209 публикаций, только 77 602 доставки при p99
публикации 3.6 мс. Брокер принимал и подтверждал всё; не успевал отдать подписчику.

**Пропускная способность упирается в однопоточный брокер.** QoS 0 выходит на плато
~50 тыс. RPS уже при 16 издателях и не растёт до 128: это потолок одного ядра, а не
масштабирование клиентов. QoS 1/2 дают 23–44 тыс. RPS и убывают с ростом числа
издателей из-за роста p99 (0.18 → 12.7 мс).

**QoS-эффекты выражены ожидаемо.** QoS 2 примерно в 2 раза медленнее QoS 1 при том
же числе издателей (23 против 44 тыс. RPS) — цена четырёхшагового handshake.
Разница между payload 16 и 256 байт незначительна (< 1 %): обработка на стороне
брокера не зависит от размера сообщения в этом диапазоне.

## 4. Ограничения этого прогона

1. **Хост не является изолированным измерительным стендом.** На нём работала
   графическая сессия (VS Code, xrdp, lightdm). Часть попыток отвергнута guard'ом
   за разрывы в сэмплировании (до 7.3 с при пределе 3 с). Повторные попытки
   восстанавливали точки, но это ослабляет чистоту измерения.
2. **`--maximum-guard-interval 3`** (вместо 1.25 с) и `--max-attempts 8` (вместо 3) —
   отклонения от значений по умолчанию, вызванные пунктом 1.
3. **Сетевой гейт не применялся**: брокер работает на loopback, физической полосы
   нет, поэтому порог сети равен `null` (информационный режим). Сетевая ёмкость не
   измерялась.
4. **Лимит памяти не enforceable.** Контроллер записал
   `memoryLimitEnforcement: not-enforced-native`: создать cgroup v2
   `/sys/fs/cgroup/mqttbenchmark-<pid>` непривилегированному пользователю запрещено.
   Записано честно, но 4 GiB-лимит фактически не действовал.
5. **Брокер и генератор нагрузки делят один хост.** Даже при `singleCorePinned`
   генератор занимает остальные ядра, поэтому измерялась связка «брокер + генератор
   на одной машине», а не изолированный брокер.
6. QoS 0 не имеет латентности по определению и исключён из калибровки.

## 5. Что можно и что нельзя использовать

Пригодно для калибровки (пакет публикации исправен, покрытие 72/72, provenance
зафиксирован):

- `completedRps`/`attemptedRps` для QoS 0 и QoS 1/2 при 1 издателе;
- латентность публикации QoS 1/2 (p50/p99);
- нулевой `publishFailureRate` как характеристика приёма.

Непригодно без переделки стенда:

- `deliveryLossRate` для точек с ≥ 16 издателями — артефакт единственного подписчика;
- любые выводы о сетевой ёмкости;
- сравнение с другими брокерами: стенд не изолирован и не имеет воспроизводимых
  ресурсных ограничений.

## 6. Рекомендации

1. Развести генератор и брокер по разным физическим машинам (требование
   `docs/test-stand-architecture.md`), либо сократить матрицу до 1–16 издателей,
   где потери нулевые.
2. Увеличить число подписчиков пропорционально издателям, иначе `deliveryLossRate`
   всегда измеряет подписчик, а не брокер.
3. Пересмотреть критерий `drainReason: quietPeriod`: завершать дренаж по тишине
   допустимо только когда очередь брокера пуста; иначе потери неотличимы от
   непрочитанного бэклога.
4. Запускать матрицу на выделенном хосте без рабочего стола, чтобы вернуть guard
   к 1.25 с и `--max-attempts` к 3.

## 7. Воспроизведение

```bash
# 1. Закрепить идентичность брокера в инвентаре стенда.
pwsh scripts/PinNativeExecutable.ps1 \
  -StandPath  config/broker-stand.native-mosquitto.json \
  -Executable /sbin/mosquitto

# 2. Полная матрица (72 ключа). Отклонения от умолчаний — см. раздел 4.
dotnet run --project src/EntityFX.MqttBenchmark.Cli -- matrix \
  --config   config/benchmark-campaign.native-mosquitto.json \
  --stand    config/broker-stand.native-mosquitto.json \
  --campaign results/campaign-mosquitto-local \
  --benchmark-repo . \
  --maximum-guard-interval 3 \
  --max-attempts 8

# 3. Агрегация. Бюджет попыток обязан совпадать с записанным.
dotnet run --project src/EntityFX.MqttBenchmark.Cli -- aggregate \
  --config config/benchmark-campaign.native-mosquitto.json \
  --stand  config/broker-stand.native-mosquitto.json \
  --raw    results/campaign-mosquitto-local \
  --output results/aggregated \
  --max-attempts 8
```

Требуется ~50 ГБ на артефакты: каждая попытка пишет `publishes.ndjson` и
`deliveries.ndjson` построчно (~244 байта на публикацию). Каталог результатов
должен находиться на диске, а не в `tmpfs`.
